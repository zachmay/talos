Create `agent/Dockerfile.base`:
```dockerfile
FROM node:22-alpine AS base

# Create non-root user
RUN addgroup -S agent && adduser -S agent -G agent -u 1000

WORKDIR /app

# Install deps at build time — remove cache in same layer to keep image lean
COPY package*.json ./
RUN npm ci --only=production --cache /tmp/npm-cache && rm -rf /tmp/npm-cache

# Copy compiled source (build step happens before docker build in CI, or use COPY src + tsc here)
COPY src/ ./src/

# Mount points: /app/agent (profile, read-only bind), /app/workspace (tmpfs), /tmp (tmpfs)
RUN mkdir -p /app/agent /app/workspace /tmp && chown agent:agent /app/agent /app/workspace

USER agent

ENTRYPOINT ["node", "--experimental-specifier-resolution=node", "src/entrypoint.js"]
```

Create `agent/Dockerfile.claude`:

FROM talos-agent-base AS claude

Create `agent/Dockerfile.ollama`:

Note: Provider Dockerfiles extend from `talos-agent-base` local image tag. In compose, each is built with `context: .` and `dockerfile: agent/Dockerfile.${AGENT_PROVIDER:-claude}`. This means base must be built first or all Dockerfiles must be self-contained. Make Dockerfile.claude/openrouter/ollama self-contained by using multi-stage: each starts `FROM node:22-alpine AS base` with the same base setup, then a provider-specific final stage. This avoids the local-tag dependency ordering problem.

Alternatively: Use a single multi-stage Dockerfile with named stages and compose `target:` field. But per CONTEXT.md decision, use separate Dockerfile.{provider} files. To make this work without a pre-built base, each provider Dockerfile repeats the base setup (acceptable for 3 files, avoids build-order coupling).

Simplest approach: Each `Dockerfile.{provider}` is fully self-contained (copies base setup + adds provider ENV). Document that this is intentional duplication to avoid local image tag coupling.

  <action>
Create `agent/seccomp-standard.json`: Use Docker's default seccomp profile as the base. Download from https://github.com/moby/moby/blob/master/profiles/seccomp/default.json and save as `agent/seccomp-standard.json`. This is Docker's hardened default that blocks ~44 dangerous syscalls. Do not create a custom profile from scratch (per research: don't hand-roll seccomp). The file should be the standard Docker default seccomp JSON.

Add the `agent` service to `docker-compose.yml` (which already has db and mcp services from Phases 1-2). Add as a new service block:

```yaml
  agent:
    build:
      context: .
      dockerfile: agent/Dockerfile.${AGENT_PROVIDER:-claude}
    read_only: true
    tmpfs:
      - /app/workspace:mode=755,uid=1000,gid=1000
      - /tmp:mode=1777
    security_opt:
      - no-new-privileges:true
      - seccomp:./agent/seccomp-standard.json
    cap_drop:
      - ALL
    networks:
      - frontend
    environment:
      - AGENT_PROFILE=${AGENT_PROFILE:-base-agent}
      - AGENT_LLM_PROVIDER=${AGENT_LLM_PROVIDER:-claude}
      - AGENT_LLM_MODEL=${AGENT_LLM_MODEL:-claude-sonnet-4-6}
      - MCP_SERVER_URL=${MCP_SERVER_URL:-http://mcp:3000/mcp}
    secrets:
      - agent_llm_key
      - agent_api_key
    deploy:
      resources:
        limits:
          cpus: '${AGENT_CPU_LIMIT:-1.0}'
          memory: '${AGENT_MEMORY_LIMIT:-512M}'
    restart: on-failure:5
    volumes:
      - type: bind
        source: ./agents/${AGENT_PROFILE:-base-agent}
        target: /app/agent
        read_only: true
    stdin_open: true
    tty: true
    depends_on:
      - mcp
```

Also add `agent_llm_key` and `agent_api_key` to the top-level `secrets:` block in docker-compose.yml (as file-based secrets pointing to the Docker secrets directory, consistent with Phase 1 pattern).

For the `strict` gVisor profile, add a separate service that extends agent with `runtime: runsc` under `profiles: [strict]`. Document clearly in a comment that this requires gVisor installed on the Linux host.
